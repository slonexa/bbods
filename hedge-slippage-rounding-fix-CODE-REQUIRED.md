## Фикс 1: средневзвешенная цена по глубине стакана вместо top-of-book

**Файл:** `collectors/polymarket.py`, метод, где сейчас:
```python
ua = min((float(x["price"]) for x in u_asks), default=0.0)
da = min((float(x["price"]) for x in d_asks), default=0.0)
```
Это берёт только лучшую котировку (verified: живой пример дал 66¢ на экране vs 68¢ реального
исполнения на $65 — расхождение из-за того, что берётся только верхний уровень стакана).

**Что сделать:**
1. Написать функцию `compute_avg_fill_price(asks: list, target_usd: float) -> float`:
   - `asks` — список уровней `[{"price": ..., "size": ...}, ...]`, отсортированный по цене
     по возрастанию (или отсортировать явно перед использованием).
   - Идти по уровням от лучшей цены вверх, накапливая объём в USD (`price * size` на уровне,
     учитывая что `size` обычно в токенах/долях, а не в USD — свериться с реальным форматом
     ответа CLOB API `https://clob.polymarket.com/books`, доступным полем `size`).
   - Как только накопленный объём достигает `target_usd` — вернуть средневзвешенную цену по
     фактически использованным уровням (не просто последний использованный уровень).
   - Если суммарной глубины стакана не хватает на `target_usd` — вернуть `None`/явный флаг
     "недостаточно ликвидности", не тихо экстраполировать за пределы видимого стакана.
2. Использовать эту функцию вместо `min(...)` там, где сейчас берётся `ua`/`da`, передавая
   туда предполагаемый размер ставки (для расчёта в Top Spreads / общей таблице — можно взять
   стандартный тестовый размер, например $50-100, раз конкретная сумма пользователя заранее
   неизвестна; для модалки "Расчёт" — уже реальную сумму, которую ввёл пользователь).
3. В ответе коллектора добавить оба значения: `best_ask` (как раньше, для быстрого сравнения)
   и `avg_fill_price` (новое, для точного расчёта хеджа) — не заменять одно другим полностью,
   чтобы не потерять информацию, показывать в UI то значение, которое уместно контексту.

## Фикс 2: округление ставки Bybit до целого доллара

**Файлы:** `engine/spread.py` (расчёт `stake_pos_pct`/`stake_neg_pct` или где считается финальный
`stake_a` в долларах) и/или `dashboard/main.py` (если округление логичнее делать на уровне API
перед отдачей в UI).

**Что сделать:**
1. После расчёта "идеального" сплита ставок (например `stake_a = $34.6`, `stake_b = $65.4`) —
   если `platform_a` (или та нога, что соответствует Bybit) требует целую сумму: округлить
   `stake_a` до ближайшего целого (`round()`, не `floor`/`ceil` без разбора — брать то
   направление округления, которое даёт меньший итоговый дисбаланс хеджа, сравнить оба варианта
   явно, не гадать).
2. Под уже округлённую целую `stake_a` пересчитать точную `stake_b` заново (используя
   `avg_fill_price` из Фикса 1) — то есть сначала фиксируем целое число на Bybit, потом уже под
   него подгоняем дробную сумму на Polymarket, а не считаем оба "идеально" и округляем постфактум.
3. Учитывать минимум Bybit — 5 USDT (из официального описания продукта Bybit Odds) — при
   округлении не давать `stake_a` уйти ниже 5.
4. В ответе/UI показывать итоговый пересчитанный `hedge_margin` уже с учётом округления — не
   показывать "идеальную" цифру, которую пользователь физически не сможет ввести на Bybit.
