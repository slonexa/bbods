# Скелет проекта: сравнение котировок prediction markets (Bybit / Polymarket / MEXC)

## Цель MVP
Собирать котировки по эквивалентным событиям с нескольких площадок, считать спред между
подразумеваемыми вероятностями, показывать результат на локальной HTML-странице с автообновлением.
Без официальных API — через внутренние эндпоинты, которые дёргает сам фронтенд площадок.

---

## 1. Архитектура (4 независимых модуля)

```
/collectors      -- по одному модулю на площадку, отдают унифицированный формат
/normalizer       -- сопоставление событий между площадками (event matching)
/engine           -- расчёт спреда, фильтр по минимальному порогу, история
/dashboard         -- локальный сервер + HTML-страница с автообновлением
```

Модули общаются только через общий формат данных (см. ниже) — так можно менять/добавлять
площадки, не трогая остальное.

---

## 2. Collectors — как достать котировки без публичного API

Шаги для каждой площадки одинаковые:

1. Открыть страницу с рынками в браузере (DevTools → вкладка Network → фильтр Fetch/XHR или WS).
2. Найти внутренний эндпоинт, который фронт дёргает для обновления цен (обычно `/api/...` JSON
   или WebSocket-канал). Он не документирован публично, но по факту это тот же REST/WS, которым
   пользуется сайт — трафика к нему обычно не больше, чем если бы юзер сам листал страницу руками.
3. Повторить запрос через `requests`/`httpx` с нужными заголовками (User-Agent, иногда нужен
   Referer/Origin). Проверить, не требует ли эндпоинт авторизационный токен из cookie/localStorage.
4. Если данные рендерятся только через JS без отдельного эндпоинта (SSR без XHR) — тогда headless
   браузер (Playwright), но это последний вариант: медленнее, тяжелее, легче спалиться.

**Важно про частоту опроса:** начинай с интервала 5–15 секунд на площадку, не с сотен
запросов в секунду. Частый polling с одного IP — почти гарантированный rate-limit/капча.
Если требуется больше скорости — WebSocket-подписка вместо polling, это менее заметно
и естественно для площадки (так и работает настоящий фронтенд).

**Площадки на старте:**
- **Polymarket** — CLOB имеет официальный публичный API (можно использовать честно, не в обход,
  задокументирован разработчиками Polymarket).
- **Bybit Odds / Bybit Prediction** — продукты запущены недавно (Odds — сентябрь 2026, Prediction —
  июнь 2026), публичного API может не быть вовсе. Смотреть Network при листании
  bybit.com/ru-RU/trade/odds/ и bybit.com/en/prediction/.
- **MEXC Prediction Market** — тоже смотреть через DevTools, публичный API не гарантирован.

Формат, который должен отдавать каждый collector:

```json
{
  "platform": "bybit_odds",
  "market_id": "BTCUSDT-UPDOWN-2026-09-30",
  "raw_title": "BTC price up by Sep 30, 18:00 UTC",
  "outcome": "up",
  "implied_probability": 0.57,
  "expiry": "2026-09-30T18:00:00Z",
  "fetched_at": "2026-09-22T10:15:03Z"
}
```

## 3. Normalizer — сопоставление событий (самая сложная часть)

Без этого шага сравнение бессмысленно: нужно не перепутать разные события за "одинаковые".

- **Крипто-таргеты (BTC/ETH up/down, price target, range)** — сопоставлять программно по
  тройке (актив, тип контракта, уровень/направление, время экспирации с точностью до минуты).
  Это автоматизируется полностью, разъезжаться могут только формулировки времени (таймзоны!).
- **Спортивные/событийные рынки** — сложнее: разные площадки формулируют условие по-разному.
  На старте — ручная таблица маппинга (`event_map.json`), где ты вручную привязываешь
  `market_id` с одной площадки к `market_id` с другой. Автоматический fuzzy-match по названию
  можно добавить позже, но на MVP не усложняй.
- Обязательно сверяй **источник резолюции** (какой оракул/фид цены признаётся окончательным) —
  если он разный, это не одно и то же событие, даже если формулировка похожа.

## 4. Engine — расчёт спреда

**Важно: тип рынка определяет формулу.** Bybit Odds — фикс-прайс контракт (коэффициент
фиксируется при входе, без early exit), Polymarket — непрерывный рынок (AMM/ордербук, цена и
твоя позиция меняются, можно выйти раньше). Это два разных инструмента, считать их одной
формулой нельзя. Добавляй в схему collector'а поле `market_type: "fixed_odds" | "continuous"`.

### 4.1 Fixed-odds vs fixed-odds (например, Bybit Up/Down vs аналог на другой CEX)

Классическая surebet-математика. Для двух взаимоисключающих исходов с десятичными
коэффициентами `O_a` и `O_b`:

```
edge = 1 - (1/O_a + 1/O_b)
```

Гарантированный плюс есть только если `edge > 0` (сумма обратных коэффициентов < 1).
На одной и той же площадке `1/O_a + 1/O_b`, как правило, **> 1** (это и есть маржа площадки,
зашитая в оба коэффициента) — ставить в обе стороны на одном и том же рынке одной и той же
площадки почти всегда гарантированный минус. Плюс возможен только между **разными** площадками,
если их оценки вероятности разошлись. Чтобы зафиксировать одинаковый выигрыш независимо от
исхода, делишь ставку так:

```
stake_a * O_a = stake_b * O_b = total_payout
```

**Критично для fixed_odds×fixed_odds:** обе площадки должны иметь тот же таймфрейм экспирации
(секунда в секунду) и тот же price index — иначе это не арбитраж, а ставка на расхождение
ценовых фидов (см. раздел 8.1). Для Bybit'овского 5/15-мин Up/Down прямого аналога с тем же
окном пока ни на одной другой площадке не подтверждено — приоритет здесь низкий, пока не
найдена реальная пара с совпадающим таймфреймом.

### 4.2 Fixed-odds vs continuous (например, Bybit Target-по-дате vs Polymarket)

Тут наоборот, у второй площадки цена/вероятность двигается до момента резолюции. Формула та же
идея (сравниваем implied probability = 1/O с текущей ценой шеры на continuous-площадке), но:

- Фиксируешь `O` на Bybit в момент входа, а на Polymarket цену нужно поймать в ту же секунду —
  иначе спред считается по несинхронным данным.
- Раз нельзя выйти из Bybit-позиции раньше времени, весь риск на continuous-ноге держишь до
  экспирации Bybit-контракта без возможности динамически перехеджироваться, если Polymarket
  успеет уйти в другую сторону.
- Дуют разные форматы контракта: Bybit "Target к дате" (выше/ниже одного страйка) ближе всего
  структурно к обычному Polymarket "will X hit $Y by [date]" — с этой пары стоит начинать
  матчинг, а не с 5/15-минутки, для которой у Polymarket просто нет аналога по таймфрейму.
- Range-контракт (внутри/вне диапазона) — это комбинация двух порогов, на Polymarket
  реплицируется через **две** позиции, а не прямой 1:1 маппинг. Оставь на после MVP.

### 4.3 Общая формула спреда после костов

```
spread = edge_from_above - (fee_A + fee_B + estimated_slippage)
```

### 4.4 Latency-паттерн: fixed-odds площадка как "живой" инструмент с лагом

Отдельный от 4.1–4.3 случай: Bybit пересчитывает коэффициент в реальном времени внутри окна
(от текущей цены и оставшегося времени, как дельта бинарного опциона). Если цена BTC уже
сдвинулась и это уже отражено в цене на continuous-площадке (Polymarket), а Bybit ещё не успел
обновить свой коэффициент под свежую цену — в этот момент открытие на Bybit даёт положительное
ожидание не из-за суммы коэффициентов, а из-за **лага конкретно Bybit** в обновлении цены.

Это принципиально другой паттерн, не путать с хеджем:
- **Ловля лага** — самостоятельная сделка с положительным EV, работает только пока Bybit не
  обновил коэффициент. Требует WebSocket и реакции в пределах секунды-двух, поллинг раз в
  5–15 сек для этого бесполезен.
- **Хедж уже открытой позиции** противоположной стороной — фиксирует текущий результат, но сам
  по себе не источник профита, если обе ноги оценены рынком честно (это нормальный риск-
  менеджмент, но не "вилка из воздуха").

**Перед тем как строить инфраструктуру под это** — самое дешёвое: залогировать пару часов, как
часто реально обновляется отображаемый коэффициент у Bybit относительно тиков реальной цены
BTC (эталон — любой публичный тикер). Если коэффициент дёргается почти в реальном времени
(суб-секунда) — лага нет, паттерн не работает. Если виден лаг в 1–3+ секунды — вот это и есть
потенциальный edge, и уже тогда имеет смысл вкладываться в низколатентную инфраструктуру
конкретно под него.

### 4.5 Моментум/сигнальные идеи (V2, не арбитраж — проверяется статистикой)

Отдельная категория идей от предыдущих: использовать движение цены на одной площадке
(например, часовой рынок Polymarket) как сигнал для входа в короткий fixed-odds контракт
на другой (Bybit 5/15 мин) в направлении уже начавшегося движения. **Это не арбитраж** —
Polymarket-коэффициент на таком рынке это просто производная от той же цены BTC, отдельной
информации он не добавляет; по сути идея сводится к "войти в Bybit по направлению недавнего
импульса цены" — обычная моментум-ставка, без гарантии исхода. Крипта на 5–15-мин окнах
славится разворотами, и коэффициент Bybit, вероятно, уже что-то учитывает из недавней
динамики в своей модели — так что эдж тут не логический (как в surebet), а статистический,
и доказывается только на истории, а не "на глаз".

**Как проверять:** engine из MVP (раздел 4.2, Target-по-дате) уже логирует историю цен —
не выбрасывай сырые тики, пиши абсолютно всё (не только найденные спреды) в отдельную таблицу
`price_history`. Когда наберётся достаточно данных, можно прогнать бэктест: "после резкого
движения X% за час, как часто следующие 5–15 минут продолжали то же направление против того,
как часто разворачивались" — и уже по факту, а не по ощущению, решать, стоит ли строить под
это отдельный сигнальный модуль.

- Считай спред **после** вычета комиссий и ожидаемого проскальзывания, а не по сырым котировкам —
  иначе бо́льшая часть "вилок" будет фантомной.
- Держи порог алерта (например, спред > 2%) настраиваемым, не хардкодь.
- Пиши каждую находку в простую БД (SQLite достаточно) — потом на исторических данных увидишь,
  насколько часто и насколько крупные вилки реально появляются, прежде чем усложнять до автотрейда.

Таблица SQLite, для старта хватит одной:

```sql
CREATE TABLE spreads (
  id INTEGER PRIMARY KEY,
  event_key TEXT,
  platform_a TEXT, prob_a REAL,
  platform_b TEXT, prob_b REAL,
  spread_after_fees REAL,
  detected_at TEXT
);
```

## 5. Dashboard — без Telegram, просто HTML

Самый простой вариант без лишней инфраструктуры:

1. Маленький локальный сервер (Python `http.server` + один эндпоинт `/api/spreads`, отдающий
   JSON из SQLite; или FastAPI, если хочешь удобнее) — крутится рядом с collectors.
2. Статический `index.html` с обычным `fetch('/api/spreads')` раз в 5–10 секунд и перерисовкой
   таблицы (без фреймворков — на MVP не нужно, чистый JS хватает).
3. Строка на topline: платформа A / платформа B / событие / спред после комиссий / время
   обнаружения. Сортировка по убыванию спреда.

Это даёт тебе рабочий дашборд без единой внешней зависимости — только твой локальный процесс.

## 6. Порядок работы (рекомендуемый)

1. Написать один collector (например, Polymarket через их официальный API — проще всего для старта).
2. Написать второй collector (Bybit Odds) — найти реальный эндпоинт через DevTools.
3. Вручную сопоставить 5–10 событий в `event_map.json`.
4. Engine + SQLite + HTML-дашборд.
5. Погонять так пару дней **без автотрейда**, посмотреть на реальную частоту и размер вилок
   после комиссий — это покажет, стоит ли вообще усложнять до автотрейда.

### 8.1 Новая ниша: 5-минутные BTC/ETH up/down контракты на CEX

Отдельно от классических prediction markets (Polymarket/Kalshi-стиль, события на дни/недели)
появилась целая волна **ультра-коротких контрактов** (5–15 минут) прямо внутри крупных CEX:

- OKX — `trade-events/btc-updown-5min`
- Gate.com — `trade-events/btc-updown-5m` (помечено "New")
- Bybit — Odds (Up/Down, Target, Range)
- MEXC — `prediction.mexc.com/prediction-markets/up-down` (5 Min / 15 Min разделы)

**Важная оговорка, критичная для матчинга:** у каждой из этих площадок, скорее всего, свой
mark-price фид и своё окно старта 5-минутки — нет гарантии, что они стартуют в одну и ту же
секунду и считают от одного и того же индекса цены BTC/ETH. Это значит, что расхождение между
ними может быть **не безрисковым арбитражем**, а просто шумом из-за разных источников цены —
то есть фактически торговля неэффективностью одной площадки относительно реального рынка, а не
чистая вилка. Первое, что нужно проверить при сборе данных с каждой такой площадки: (1) какой
именно price index используется как источник расчёта, (2) когда именно стартует и заканчивается
окно контракта (секунда в секунду), и только потом матчить это как "одно событие" с другой CEX.
Никакой готовый скринер (все ниже) этот сегмент вообще не мониторит — площадки слишком новые.

### 8.2 Ещё найденные тулзы-агрегаторы (для справки, не покрывают CEX-продукты выше)

- **doxa.pro** — "Get the Best Price Across All Prediction Markets", агрегатор с авто-исполнением
  (тот же класс, что agg.market/Senal — ищет лучшую цену и сам роутит сделку).
- **oxygendelta.com** — бесплатный реалтайм-сканер: Polymarket, Kalshi, Predict.fun, Opinion,
  Probable.
- **agg.market** (Snag Solutions) — агрегирует Polymarket/Kalshi/Myriad/Limitless/Opinion в один

Все они — тот же классический сегмент (Polymarket/Kalshi-стиль), 5-минутные CEX-контракты никто
из них не трогает. Подтверждает вывод из раздела 7: точка входа — именно этот новый сегмент.

## 9. Риски, которые стоит держать в голове

- Скрейпинг внутренних (недокументированных) эндпоинтов может нарушать ToS площадки — в худшем
  случае бан аккаунта. Не спамь запросами, не выдавай себя за официальный клиент агрессивно.
- Событие может разрешиться по-разному на разных площадках (разный оракул/оговорки в правилах) —
  это главный источник "вилок", которые на самом деле не вилки.
- Если параллельно участвуешь в конкурсе на объём — проверь его правила отдельно: многие биржи
  явно запрещают wash trading / арбитражные схемы под бонусные акции и просто аннулируют начисления
  или банят аккаунт при обнаружении.
